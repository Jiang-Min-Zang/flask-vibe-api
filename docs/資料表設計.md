# 個人記帳本資料庫設計規格書（Supabase PostgreSQL）

本文件為個人專用記帳本（Personal Ledger）之關聯式資料庫設計規格書，底層採用 Supabase 託管之 PostgreSQL。未來後端將由 Flask 搭配 SQLAlchemy 進行資料存取與業務邏輯封裝。

---

## 一、 架構設計概述與全域規則

### 1. 核心概念架構
本系統將個人財務帳務收斂為「四本冊子」與「金流帳戶體系」：
- **金流帳戶與移轉**：所有實際資金停留於帳戶（現金、銀行、信用卡、券商交割戶）。帳戶間的資金調撥屬於「移轉（Transfers）」，**移轉絕非入帳，亦非花費**。
- **入帳冊（Incomes）**：外部資金流入（如薪水、獎金、利息、退款、發票中獎獎金、股票現金股利、減資退回款項）。
- **花費冊（Expenses）**：資金對外支出。消費發生日（消費日）與信用卡實際扣款結算日可以不同。
- **投資冊（Investments）**：記錄標的基本資訊與各類型交易（買進、賣出、配股、配息、分割、合併、減資等）。**持有股數與平均成本一律由交易動態計算，不儲存為可修改欄位**。
- **發票冊（Invoices）**：記錄台灣統一發票（號碼為 2 碼大寫英文加 8 碼數字）及其品項明細，支援對獎與獎金入帳連動。

### 2. 全域欄位與命名規範
- **大小寫規範**：資料表名稱、欄位名稱一律採用小寫英文（snake_case），單字間以底線分隔。
- **主鍵設計**：每一張表的主鍵欄位統一為 `id`，型別為 64 位元整數（`BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`），由資料庫系統自動產生，建立後不可變更。
- **時間戳記**：
  - 每一張表皆包含 `created_at` 與 `updated_at`。
  - `created_at`：型別為 `TIMESTAMPTZ`，必填，預設值由資料庫自動填入當前 UTC 時間（`DEFAULT timezone('utc', now())`）。
  - `updated_at`：型別為 `TIMESTAMPTZ`，必填，**在資料更新時由應用程式（API）明確寫入當前 UTC 時間**。
  - 商業業務日期時間（如 `received_at`、`spent_at`、`transacted_at`）均採用帶時區之 `TIMESTAMPTZ`。
- **金額與數值型別**：
  - 金額、單價一律採用高精度定點數 `NUMERIC(16, 4)`，避免浮點數誤差，可容納小數。
  - 投資股數採用 `NUMERIC(16, 4)`，以精確支援碎股、零股交易。
  - 匯率採用 `NUMERIC(16, 6)`。
- **幣別與匯率規則**：
  - 幣別代碼一律為 3 碼大寫字母（符合 ISO 4217，如 `TWD`, `USD`, `JPY`）。
  - 每一筆涉及跨幣別的記錄（入帳、花費、投資交易、帳戶移轉）均包含「換算為新台幣（TWD）的匯率」欄位 `exchange_rate`。
  - **新台幣本身匯率強制為 1.000000**（由資料庫 CHECK 約束強制檢驗）。
- **外部參照與刪除完整性約束**：
  - 嚴格落實**父列被參照時禁止刪除**（`ON DELETE RESTRICT`），防止歷史金流孤立或帳目失衡。
  - **全系統僅有一處級聯刪除例外**：`invoice_items`（發票品項）之外鍵參照 `invoices(id)` 設置 `ON DELETE CASCADE`，符合「品項跟著發票一起消失」之規格。

## 二、 資料表詳細設計

本系統共有 12 張核心實體表。

### 1. `accounts`（資金帳戶表）
- **記什麼**：個人持有的實體與虛擬資金帳戶（現金皮夾、銀行活存/外幣、信用卡、券商交割戶等）。
- **為什麼單獨成表**：所有金流（花費扣款、薪資入帳、移轉調撥、投資交割）必須落在具體帳戶上。帳戶具備獨立的型態、計價幣別與啟用狀態，是資產負債計算的核心基準。

#### 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | BIGINT | 必填 | PRIMARY KEY | 主鍵，系統自動產生之整數 |
| `name` | VARCHAR(50) | 必填 | UNIQUE | 帳戶名稱（如：玉山台幣活存、中信LinePay卡、皮夾現金、富邦交割戶） |
| `account_type` | VARCHAR(20) | 必填 | 無 | 帳戶類型：`cash`（現金）, `bank`（銀行）, `credit_card`（信用卡）, `brokerage`（券商交割戶） |
| `currency` | CHAR(3) | 必填 | 無 | 帳戶本位幣別（3 碼 ISO，如 `TWD`, `USD`） |
| `initial_balance` | NUMERIC(16, 4) | 必填 | 無 | 啟用時初始餘額（預設 `0.0000`） |
| `description` | TEXT | 可空 | 無 | 帳戶備註或說明 |
| `is_active` | BOOLEAN | 必填 | 無 | 是否使用中（預設 `TRUE`，停用代替刪除） |
| `created_at` | TIMESTAMPTZ | 必填 | 無 | 建立時間，資料庫預設 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 無 | 最後更新時間，由 API 寫入 |

#### 外鍵與約束
- **資料庫約束**：
  - `CHECK (account_type IN ('cash', 'bank', 'credit_card', 'brokerage'))`
  - `CHECK (currency ~ '^[A-Z]{3}$')`
  - `UNIQUE (name)`
- **API 寫入前檢查**：
  - 帳戶名稱前後空白過濾。
  - 幣別代碼是否符合 ISO 4217 標準。

---

### 2. `transfers`（帳戶移轉表）
- **記什麼**：資金在兩個帳戶之間的內部調撥記錄（如 ATM 提款、銀行互轉、轉入交割戶、信用卡結清繳款、外幣換匯）。
- **為什麼單獨成表**：移轉是帳戶間資產形態的變更，既不是「入帳」（總資產未增加），也不是「花費」（總資產未消耗）。將移轉自收支獨立，能保證報表不會虛增收支。

#### 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | BIGINT | 必填 | PRIMARY KEY | 主鍵，系統自動產生之整數 |
| `from_account_id` | BIGINT | 必填 | 無 | 轉出帳戶 ID，外鍵指向 `accounts(id)` |
| `to_account_id` | BIGINT | 必填 | 無 | 轉入帳戶 ID，外鍵指向 `accounts(id)` |
| `transferred_at` | TIMESTAMPTZ | 必填 | 無 | 移轉發生時間 |
| `from_amount` | NUMERIC(16, 4) | 必填 | 無 | 轉出金額（以轉出帳戶幣別計） |
| `to_amount` | NUMERIC(16, 4) | 必填 | 無 | 轉入金額（以轉入帳戶幣別計，換匯時可與轉出金額不同） |
| `fee` | NUMERIC(16, 4) | 必填 | 無 | 跨行/跨國手續費（預設 `0.0000`） |
| `exchange_rate` | NUMERIC(16, 6) | 必填 | 無 | 外幣換算成台幣匯率（台幣為 `1.000000`） |
| `note` | TEXT | 可空 | 無 | 移轉備註說明 |
| `created_at` | TIMESTAMPTZ | 必填 | 無 | 建立時間，資料庫預設 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 無 | 最後更新時間，由 API 寫入 |

#### 外鍵與約束
- **外鍵規則**：
  - `FOREIGN KEY (from_account_id) REFERENCES accounts(id) ON DELETE RESTRICT`
  - `FOREIGN KEY (to_account_id) REFERENCES accounts(id) ON DELETE RESTRICT`
- **資料庫約束**：
  - `CHECK (from_account_id <> to_account_id)`：禁止同一帳戶轉給自己。
  - `CHECK (from_amount > 0)`
  - `CHECK (to_amount > 0)`
  - `CHECK (fee >= 0)`
  - `CHECK (exchange_rate > 0)`
- **API 寫入前檢查**：
  - 轉出帳戶非信用卡（除非是預借現金特殊作業）且餘額是否充足（若為無透支銀行帳戶）。
  - 若轉出與轉入幣別皆為 `TWD`，強制設定 `exchange_rate = 1.000000`。

### 3. `income_categories`（入帳分類表）
- **記什麼**：收入的商業分類標籤（如：薪資所得、年終獎金、利息所得、發票中獎、現金股利、退款補償）。
- **為什麼單獨成表**：依規格要求「入帳與花費的分類分開，名稱各自不能重複」。將入帳分類獨立成表，避免與花費分類混淆，且可獨立管理說明與排序。

#### 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | BIGINT | 必填 | PRIMARY KEY | 主鍵，系統自動產生之整數 |
| `name` | VARCHAR(50) | 必填 | UNIQUE | 分類名稱（在入帳分類中不可重複） |
| `description` | TEXT | 可空 | 無 | 分類補充說明 |
| `created_at` | TIMESTAMPTZ | 必填 | 無 | 建立時間，資料庫預設 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 無 | 最後更新時間，由 API 寫入 |

#### 外鍵與約束
- **資料庫約束**：
  - `UNIQUE (name)`

---

### 4. `expense_categories`（花費分類表）
- **記什麼**：支出的商業分類標籤（如：餐飲外食、日常用品、交通運輸、娛樂休閒、居住水電、醫療保險）。
- **為什麼單獨成表**：與入帳分類分離，具備獨立命名空間，確保花費統計維度清晰。

#### 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | BIGINT | 必填 | PRIMARY KEY | 主鍵，系統自動產生之整數 |
| `name` | VARCHAR(50) | 必填 | UNIQUE | 分類名稱（在花費分類中不可重複） |
| `description` | TEXT | 可空 | 無 | 分類補充說明 |
| `created_at` | TIMESTAMPTZ | 必填 | 無 | 建立時間，資料庫預設 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 無 | 最後更新時間，由 API 寫入 |

#### 外鍵與約束
- **資料庫約束**：
  - `UNIQUE (name)`

---

### 5. `incomes`（入帳冊主表）
- **記什麼**：錢流入個人資產的具體流水帳，包括工作收入、投資配息返還、發票中獎領獎等。
- **為什麼單獨成表**：記錄入帳的核心事實（金額、幣別、匯率、時間、目的帳戶）。並支援連結至發票（中獎）與投資交易（股利、減資），達成金流溯源。

#### 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | BIGINT | 必填 | PRIMARY KEY | 主鍵，系統自動產生之整數 |
| `account_id` | BIGINT | 必填 | 無 | 存入之帳戶 ID，外鍵指向 `accounts(id)` |
| `category_id` | BIGINT | 必填 | 無 | 入帳分類 ID，外鍵指向 `income_categories(id)` |
| `received_at` | TIMESTAMPTZ | 必填 | 無 | 實際入帳日期時間 |
| `amount` | NUMERIC(16, 4) | 必填 | 無 | 入帳金額（帳戶幣別） |
| `currency` | CHAR(3) | 必填 | 無 | 幣別（3 碼 ISO） |
| `exchange_rate` | NUMERIC(16, 6) | 必填 | 無 | 換算新台幣匯率（TWD 強制為 1） |
| `source_invoice_id` | BIGINT | 可空 | UNIQUE | 關聯之發票 ID，外鍵指向 `invoices(id)`。**設為 UNIQUE 保證一張發票最多一筆入帳** |
| `source_investment_transaction_id` | BIGINT | 可空 | UNIQUE | 關聯之投資交易 ID，外鍵指向 `investment_transactions(id)`。**設為 UNIQUE 保證一筆投資交易最多一筆入帳** |
| `note` | TEXT | 可空 | 無 | 入帳備註 |
| `created_at` | TIMESTAMPTZ | 必填 | 無 | 建立時間，資料庫預設 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 無 | 最後更新時間，由 API 寫入 |

#### 外鍵與約束
- **外鍵規則**：
  - `FOREIGN KEY (account_id) REFERENCES accounts(id) ON DELETE RESTRICT`
  - `FOREIGN KEY (category_id) REFERENCES income_categories(id) ON DELETE RESTRICT`
  - `FOREIGN KEY (source_invoice_id) REFERENCES invoices(id) ON DELETE RESTRICT`
  - `FOREIGN KEY (source_investment_transaction_id) REFERENCES investment_transactions(id) ON DELETE RESTRICT`
- **資料庫約束**：
  - `CHECK (amount > 0)`
  - `CHECK (currency ~ '^[A-Z]{3}$')`
  - `CHECK (exchange_rate > 0)`
  - `CHECK (currency <> 'TWD' OR exchange_rate = 1.000000)`：若幣別為 TWD，匯率必須為 1。
  - `UNIQUE (source_invoice_id)`：PostgreSQL 中 NULL 值不互斥，但非空值唯一，完美實現「一張發票至多對應一筆中獎入帳」。
  - `UNIQUE (source_investment_transaction_id)`：完美實現「一筆投資交易（現金股利或減資）至多對應一筆入帳」。
  - `CHECK (NOT (source_invoice_id IS NOT NULL AND source_investment_transaction_id IS NOT NULL))`：同一筆入帳不得同時來自發票與投資。
- **API 寫入前檢查**：
  - 若指定 `source_invoice_id`，發票狀態必須為中獎狀態（`won`），且入帳金額必須符合中獎獎金金額。
  - 若指定 `source_investment_transaction_id`，該投資交易之類型必須為 `cash_dividend` 或現金 `capital_reduction`。

### 6. `expenses`（花費冊主表）
- **記什麼**：消費支出的每一筆記錄。
- **為什麼單獨成表**：消費具備消費發生日（`spent_at`）與扣款結算日（`settled_at`）雙時間軸特性（尤其是信用卡），並可對應至發票（一張發票可對應多筆消費分攤）。

#### 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | BIGINT | 必填 | PRIMARY KEY | 主鍵，系統自動產生之整數 |
| `account_id` | BIGINT | 必填 | 無 | 支付帳戶 ID（如信用卡、現金皮夾、銀行戶），外鍵指向 `accounts(id)` |
| `category_id` | BIGINT | 必填 | 無 | 花費分類 ID，外鍵指向 `expense_categories(id)` |
| `invoice_id` | BIGINT | 可空 | 無 | 關聯之統一發票 ID，外鍵指向 `invoices(id)`。**不設 UNIQUE，允許多筆花費對應同一張發票** |
| `spent_at` | TIMESTAMPTZ | 必填 | 無 | 消費發生日期時間（如刷卡日、現金購買日） |
| `settled_at` | TIMESTAMPTZ | 可空 | 無 | 帳戶實際扣款/結算日期時間（信用卡繳款結算或請款日） |
| `amount` | NUMERIC(16, 4) | 必填 | 無 | 消費金額（支付幣別） |
| `currency` | CHAR(3) | 必填 | 無 | 幣別（3 碼 ISO） |
| `exchange_rate` | NUMERIC(16, 6) | 必填 | 無 | 換算新台幣匯率（TWD 強制為 1） |
| `merchant` | VARCHAR(100) | 可空 | 無 | 消費店家/營業人名稱 |
| `note` | TEXT | 可空 | 無 | 消費備註（如商品用途） |
| `created_at` | TIMESTAMPTZ | 必填 | 無 | 建立時間，資料庫預設 UTC |
| `updated_at` | TIMESTAMPTZ | 必填 | 無 | 最後更新時間，由 API 寫入 |

#### 外鍵與約束
- **外鍵規則**：
  - `FOREIGN KEY (account_id) REFERENCES accounts(id) ON DELETE RESTRICT`
  - `FOREIGN KEY (category_id) REFERENCES expense_categories(id) ON DELETE RESTRICT`
  - `FOREIGN KEY (invoice_id) REFERENCES invoices(id) ON DELETE RESTRICT`
- **資料庫約束**：
  - `CHECK (amount > 0)`
  - `CHECK (currency ~ '^[A-Z]{3}$')`
  - `CHECK (exchange_rate > 0)`
  - `CHECK (currency <> 'TWD' OR exchange_rate = 1.000000)`：幣別為 TWD 時匯率強制為 1。
- **API 寫入前檢查**：
  - 若 `account_id` 是現金帳戶或活期存款帳戶，預設或建議將 `settled_at` 填入與 `spent_at` 相同之時間（即時扣款）。
  - 若 `account_id` 為信用卡帳戶，`settled_at` 可先為 NULL，待結帳出帳或繳款時更新。
  - 多筆花費對應同一張發票時，**業務規格允許花費合計不必等於發票總額**（例如部分公務報銷、朋友分攤或折價券折抵）。

### 7. `invoices`（統一發票表）
- **記什麼**：台灣統一發票主體資料，記錄 10 碼發票號碼、開立時間、開獎期別、隨機碼、總金額、賣方統編及中獎狀態。
- **為什麼單獨成表**：發票具有留底與對獎的獨立生命週期。一張發票可以包含多個商品品項（一對多），也可以被多筆費用關聯。

#### 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | BIGINT | 必填 | PRIMARY KEY | 主鍵，系統自動產生之整數 |
| `invoice_number` | CHAR(10) | 必填 | 無 | 發票號碼：2 碼大寫英文字軌 + 8 碼數字（如 `AB12345678`） |
| `issued_at` | TIMESTAMPTZ | 必填 | 無 | 發票開立日期時間 |
| `period` | VARCHAR(7) | 必填 | 無 | 發票期別（格式：`YYYMM-MM`，如民國 115 年 1-2 月記為 `11501-02`） |
| `random_number` | CHAR(4) | 可空 | 無 | 發票隨機碼（4 碼數字，紙本/電子發票留底用） |
| `total_amount` | NUMERIC(16, 4) | 必填 | 無 | 發票開立總金額 |
| `currency` | CHAR(3) | 必填 | 無 | 幣別（預設 `TWD`） |
| `exchange_rate` | NUMERIC(16, 6) | 必填 | 無 | 換算新台幣匯率（預設 `1.000000`） |
| `seller_tax_id` | CHAR(8) | 可空 | 無 | 賣方統一編號（8 碼數字） |

### 12. `investment_transactions`（投資交易明細表）
- **記什麼**：每一筆標的之交易活動與股權變動記錄。
- **為什麼單獨成表**：依規格要求「投資記一檔標的與每一筆交易。持有股數與平均成本由交易算出」。本表完整儲存交易事件流（Event Stream），是推算持有股數與加權平均成本的唯一原始憑證。

#### 支援交易種類（`transaction_type`）
1. `buy`（買進）：增持股數，交割帳戶扣除價金與手續費。
2. `sell`（賣出）：減持股數，交割帳戶存入價金（扣除手續費與證券交易稅）。**賣出後該標的累積持有股數不得小於 0**。
3. `cash_dividend`（現金股利）：持有股數不變，收到現金股利。**可連動至 `incomes` 表記錄一筆入帳**。
4. `stock_dividend`（配股 / 股票股利）：獲得無償配發之股票，股數增加，現金流為 0。
5. `dividend_reinvestment`（股息再投入）：配發之股息直接轉為購入新股數，股數增加。
6. `stock_split`（分割）：一股分割為多股，股數按比例增加，投入成本不變，現金流為 0。
7. `stock_consolidation`（合併 / 反分割）：多股合併為一股，股數按比例減少，投入成本不變，現金流為 0。
8. `capital_reduction`（減資）：
   - 現金減資：銷除部分股數，同時退回現金予股東。**退回之現金可連動至 `incomes` 表記錄一筆入帳**。
   - 彌補虧損減資：純粹銷除股數，無現金退回。

#### 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | BIGINT | 必填 | PRIMARY KEY | 主鍵，系統自動產生之整數 |
| `target_id` | BIGINT | 必填 | 無 | 投資標的 ID，外鍵指向 `investment_targets(id)` |
| `account_id` | BIGINT | 必填 | 無 | 交割資金帳戶 ID（如券商交割戶），外鍵指向 `accounts(id)` |
| `transaction_type` | VARCHAR(30) | 必填 | 無 | 交易種類代碼（詳見上述 8 種） |
| `transacted_at` | TIMESTAMPTZ | 必填 | 無 | 交易執行/生效日期時間 |
| `shares` | NUMERIC(16, 4) | 必填 | 無 | 涉及股數變動量（絕對值，>= 0；現金股利為 0） |
| `price_per_share` | NUMERIC(16, 4) | 必填 | 無 | 每股成交單價（配股、分割、減資、純現金股利時為 0） |
| `total_amount` | NUMERIC(16, 4) | 必填 | 無 | 交易淨收付金額（買進為實付總額，賣出為實收總額，股利為實發總額，無金流時為 0） |
| `fee` | NUMERIC(16, 4) | 必填 | 無 | 券商手續費（預設 `0.0000`） |
| `tax` | NUMERIC(16, 4) | 必填 | 無 | 證交稅或政府規費（預設 `0.0000`） |
| `currency` | CHAR(3) | 必填 | 無 | 交易計價幣別（如 `TWD`, `USD`） |
| `exchange_rate` | NUMERIC(16, 6) | 必填 | 無 | 換算新台幣匯率（台幣強制為 `1.000000`） |
| `split_ratio` | NUMERIC(12, 6) | 可空 | 無 | 分割/合併/減資比例（輔助欄位，如 1 拆 2 記為 2.0；減資兩成換發 0.8 股記為 0.8） |

## 三、 餘額與持有股數計算規格（非實體可修改欄位）

為維護資料庫之一致性與稽核性（Auditability），系統嚴禁在 `accounts` 表建立可手動 UPDATE 的 `current_balance` 欄位，亦嚴禁在 `investment_targets` 表建立可修改的 `holding_shares` 或 `average_cost` 欄位。所有餘額與成本均由下列關聯列計算得出。

### 1. 帳戶即時餘額（Account Balance）計算邏輯
指定帳戶 `target_account_id` 在特定幣別下的目前餘額，計算來源為下列資料列的代數和：

$$\text{帳戶當前餘額} = \text{初始餘額} + \text{入帳總和} - \text{花費總和} + \text{轉入總和} - \text{轉出總和} + \text{投資金流淨額}$$

#### 涉及的表與欄位計算清單：
1. **初始餘額**：
   - 來自 `accounts.initial_balance`。
2. **入帳（加項）**：
   - 來自 `incomes` 表，條件為 `account_id = target_account_id`。
   - 加總金額：`SUM(incomes.amount)`。
   - *(說明：發票中獎獎金、現金股利、減資退款若已透過連動寫入 `incomes` 表，即自動計入此項，不重複統計)*。
3. **花費（減項）**：
   - 來自 `expenses` 表，條件為 `account_id = target_account_id`。
   - 若為現金/銀行帳戶，按實際支出扣減；若為信用卡帳戶，此項代表累積之未沖銷應付消費款項（負債）。
   - 扣減金額：`SUM(expenses.amount)`。
4. **帳戶移轉（轉入為加項，轉出為減項）**：
   - 轉入：來自 `transfers` 表，條件為 `to_account_id = target_account_id`，增加金額為 `SUM(transfers.to_amount)`。
   - 轉出：來自 `transfers` 表，條件為 `from_account_id = target_account_id`，扣除金額為 `SUM(transfers.from_amount)`。
5. **投資交割直接扣款（非入帳之投資金流）**：
   - 買進扣款（減項）：`investment_transactions` 中 `account_id = target_account_id` 且 `transaction_type = 'buy'`，扣除 `SUM(total_amount)`。
   - 賣出收款（加項）：`investment_transactions` 中 `account_id = target_account_id` 且 `transaction_type = 'sell'`，增加 `SUM(total_amount)`。
   - *(注意：若現金股利與減資退款已於 `incomes` 認列，則投資交易表中的該兩類金額不在投資直接收款中重複累加，避免雙重計算)*。

---

### 2. 投資持有股數（Holding Shares）計算邏輯
指定投資標的 `target_id` 目前的庫存股數，由 `investment_transactions` 表中該標的所有交易記錄按時間順序累加求得：

$$\text{目前持有股數} = \sum_{\text{該標的所有交易}} \Delta\text{shares}$$

#### 各交易類型對股數的影響（$\Delta\text{shares}$）：
| 交易類型代碼 (`transaction_type`) | 股數增減方向 | 說明 |
| :--- | :---: | :--- |
| `buy` | **$+$ shares** | 買入增加持股 |
| `sell` | **$-$ shares** | 賣出減少持股 |
| `stock_dividend` | **$+$ shares** | 無償配股增加持股 |
| `dividend_reinvestment` | **$+$ shares** | 股息再買入增加持股 |
| `stock_split` | **$+$ shares** | 依分割比率增加之淨股數（或 $舊股數 \times (ratio - 1)$） |
| `stock_consolidation` | **$-$ shares** | 反分割合併銷除之淨股數 |
| `capital_reduction` | **$-$ shares** | 減資銷除之股數 |
| `cash_dividend` | **$0$** | 純配發現金，股數完全不變 |

> **核心檢驗規則（API 在寫入前檢查）**：
> 在任意時間點 $t$，該標的截至時間 $t$ 之所有歷史交易累計股數總和必須滿足：
> $$\sum_{\tau \le t} \Delta\text{shares}_\tau \ge 0$$
> 若任何一筆 `sell`、`stock_consolidation` 或 `capital_reduction` 執行後會導致持有股數 $< 0$，API 即判定非法並拒絕寫入。

### 3. 投資平均成本（Average Cost per Share）計算邏輯
本系統採用業界標準的**「加權移動平均法（Moving Weighted Average Cost Method）」**，由歷史交易流按交易時間由早至晚依序推導。

#### 演算法計算步驟：
設第 $i$ 筆交易發生前的累積庫存股數為 $S_{i-1}$，累積總成本為 $C_{i-1}$，每股平均成本為 $P_{i-1} = \frac{C_{i-1}}{S_{i-1}}$。

1. **買進（`buy`）與股息再投入（`dividend_reinvestment`）**：
   - 股數變動：$S_i = S_{i-1} + \text{shares}_i$
   - 成本變動：$C_i = C_{i-1} + \text{total_amount}_i$（包含價金與手續費）
   - 新平均每股成本：$P_i = \frac{C_i}{S_i}$
2. **股票股利配股（`stock_dividend`）與股票分割（`stock_split`）**：
   - 股數變動：$S_i = S_{i-1} + \text{shares}_i$
   - 成本變動：$C_i = C_{i-1}$（無新增現金投入，總成本不變）
   - 新平均每股成本：$P_i = \frac{C_{i-1}}{S_i}$（股數增加，平均每股成本被稀釋攤低）
3. **股票合併（`stock_consolidation`）**：
   - 股數變動：$S_i = S_{i-1} - \text{shares}_i$
   - 成本變動：$C_i = C_{i-1}$（總成本不變）
   - 新平均每股成本：$P_i = \frac{C_{i-1}}{S_i}$（股數減少，平均每股成本提高）
4. **賣出（`sell`）**：
   - 股數變動：$S_i = S_{i-1} - \text{shares}_i$
   - 成本變動：扣減等比例持股成本，$C_i = C_{i-1} - (\text{shares}_i \times P_{i-1})$
   - 每股平均成本：**維持不變**（$P_i = P_{i-1}$）
   - 已實現損益：$\text{已實現獲利} = \text{total_amount}_i - (\text{shares}_i \times P_{i-1})$
5. **現金減資（`capital_reduction`）**：
   - 股數變動：$S_i = S_{i-1} - \text{shares}_i$
   - 成本變動：若退回現金 $R$（記錄於 `total_amount`），則總成本扣減退款金額，$C_i = C_{i-1} - R$
   - 新平均每股成本：$P_i = \frac{C_i}{S_i}$
6. **現金股利（`cash_dividend`）**：
   - 股數變動：$S_i = S_{i-1}$
   - 成本變動：視為獨立投資收益認列於 `incomes`，持股原始成本維持不變。

## 四、 統一發票期別決定與開獎對獎機制

### 1. 發票期別（Period）如何由開立日（`issued_at`）決定
台灣統一發票採**每兩個月為一期**開獎一次。本系統在資料庫與 API 中將期別統一定義為格式 `YYYMM-MM`（民國年 3 碼 + 雙月份區間）：

#### 期別換算公式與開獎時程對應：
令開立時間 `issued_at` 轉換為台灣時間（UTC+8）後的西元年為 $Y$、西元月份為 $M$：
1. **民國年換算**：$\text{ROC\_YEAR} = Y - 1911$。
2. **期別月份區間決定**：
   - 若 $M \in \{1, 2\}$：期別區間為 `01-02`，於當年 **3 月 25 日**開獎。
   - 若 $M \in \{3, 4\}$：期別區間為 `03-04`，於當年 **5 月 25 日**開獎。
   - 若 $M \in \{5, 6\}$：期別區間為 `05-06`，於當年 **7 月 25 日**開獎。
   - 若 $M \in \{7, 8\}$：期別區間為 `07-08`，於當年 **9 月 25 日**開獎。
   - 若 $M \in \{9, 10\}$：期別區間為 `09-10`，於當年 **11 月 25 日**開獎。
   - 若 $M \in \{11, 12\}$：期別區間為 `11-12`，於次年 **1 月 25 日**開獎。
3. **合成期別字串範例**：
   - 開立日為 `2026-03-15` $\to$ 西元 2026 年（民國 115 年），月份 3 月 $\to$ 期別為 `11503-04`。
   - 開立日為 `2026-12-01` $\to$ 西元 2026 年（民國 115 年），月份 12 月 $\to$ 期別為 `11511-12`。

> **執行責任標記**：
> 在發票新增或更新時，**由 API 在寫入前檢查並由開立日自動計算填入 `period` 欄位**，確保發票開立日與所屬期別永不脫節。

---

### 2. 開獎獎金資料表化機制
系統嚴格遵守「開獎獎金放在資料表，不寫死在設計說明的程式片段裡」：
- 開獎號碼登記於 `invoice_lottery_periods`。
- 每一獎別的名稱與獎金金額登記於 `invoice_lottery_prizes`。
- **對獎流程**：
  1. 對獎時，程式讀取該期 `invoice_lottery_periods` 的各獎項號碼與 `invoice_lottery_prizes` 中的各獎別獎金。
  2. 若比對中獎，將 `invoices.lottery_status` 更新為 `won`，並將 `invoices.winning_prize_id` 填入對應的 `invoice_lottery_prizes.id`。
  3. 若未中獎，將 `invoices.lottery_status` 更新為 `not_won`。

---

### 3. 中獎發票轉入帳（Incomes）連動機制
- 發票中獎後領獎，於 `incomes` 表新增一筆記錄：
  - `account_id`：存入之銀行帳戶或現金帳戶。
  - `category_id`：指向「發票中獎」分類。
  - `amount`：中獎金額（來自關聯的 `invoice_lottery_prizes.prize_amount`，或扣除印花稅後實領額）。
  - `source_invoice_id`：填入該中獎發票之 `invoices.id`。
- **限制保證**：
  - 由於 `incomes.source_invoice_id` 設有資料庫層級之 **`UNIQUE` 約束**，若試圖對同一張發票重複建立第二筆入帳，PostgreSQL 將直接阻擋報錯，在資料庫層級嚴密保證**「一張發票最多一筆入帳」**。

## 五、 投資金流與入帳連動機制

### 1. 現金股利與減資退款之入帳處理
- 投資交易登記 `cash_dividend`（現金股利）或退回現金之 `capital_reduction`（減資）：
  - 交易明細留存於 `investment_transactions`。
  - 實際領到現金時，於 `incomes` 表登記一筆入帳：
    - `account_id`：款項匯入之券商交割戶或銀行帳戶。
    - `category_id`：指向「投資收益 / 股利」或「投資本金返還」分類。
    - `amount`：實收現金金額。
    - `source_investment_transaction_id`：指向該筆 `investment_transactions.id`。
- **限制保證**：
  - 由於 `incomes.source_investment_transaction_id` 設有資料庫層級之 **`UNIQUE` 約束**，資料庫保證**「一筆交易最多一筆入帳」**。

## 六、 規則落實檢查矩陣（PostgreSQL 約束 vs API 檢查）

所有業務規則均嚴密區分其落實層級：

| 規則說明 | 落實層級 | 具體機制與約束定義 |
| :--- | :---: | :--- |
| **主鍵整數自動產生且不可改** | PostgreSQL | `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` |
| **父列被參照時禁止刪除** | PostgreSQL | 外鍵預設 `ON DELETE RESTRICT` |
| **唯一的級聯刪除例外** | PostgreSQL | `invoice_items.invoice_id REFERENCES invoices(id) ON DELETE CASCADE` |
| **建立時間由 DB 填 UTC** | PostgreSQL | `created_at TIMESTAMPTZ NOT NULL DEFAULT timezone('utc', now())` |
| **更新時間由程式寫入** | API | 由 API 在執行 UPDATE 操作時填入當前 UTC 時間戳記 |
| **帳戶名稱全域唯一** | PostgreSQL | `accounts.name UNIQUE` |
| **入帳分類名稱不重複** | PostgreSQL | `income_categories.name UNIQUE` |
| **花費分類名稱不重複** | PostgreSQL | `expense_categories.name UNIQUE` |
| **同市場標的代號不重複** | PostgreSQL | `investment_targets(market, symbol) UNIQUE` |
| **同期發票號碼不重複** | PostgreSQL | `invoices(period, invoice_number) UNIQUE` |
| **發票格式必須為 2 碼大寫英文字軌 + 8 碼數字** | PostgreSQL | `CHECK (invoice_number ~ '^[A-Z]{2}[0-9]{8}$')` |
| **幣別代碼必須為 3 碼大寫英文字母** | PostgreSQL | `CHECK (currency ~ '^[A-Z]{3}$')` |
| **新台幣匯率強制為 1.000000** | PostgreSQL | `CHECK (currency <> 'TWD' OR exchange_rate = 1.000000)` |
| **一張發票最多一筆入帳** | PostgreSQL | `incomes.source_invoice_id UNIQUE` |
| **一筆投資交易最多一筆入帳** | PostgreSQL | `incomes.source_investment_transaction_id UNIQUE` |
| **入帳來源（發票 vs 投資）互斥** | PostgreSQL | `CHECK (NOT (source_invoice_id IS NOT NULL AND source_investment_transaction_id IS NOT NULL))` |
| **移轉不得自我調撥** | PostgreSQL | `CHECK (from_account_id <> to_account_id)` |
| **金額、股數不得為負** | PostgreSQL | `CHECK (amount > 0)`, `CHECK (shares >= 0)`, `CHECK (total_amount >= 0)` |
| **投資賣出不得使持有股數小於 0** | API | **由 API 在寫入前檢查**：計算標的截至交易日之累積持股，若賣出股數大於庫存則拋錯攔截 |
| **由開立日推導發票開獎期別** | API | **由 API 在寫入前檢查**：根據 `issued_at` 依照雙月週期演算法自動推導並寫入 `period` |
| **消費日與扣款日時間邏輯** | API | **由 API 在寫入前檢查**：確認 `settled_at >= spent_at`（信用卡結算扣款日不得早於消費發生日） |
| **帳戶餘額不得非法透支** | API | **由 API 在寫入前檢查**：現金與無透支銀行帳戶支出或轉出前計算餘額是否足夠 |

## 七、 這一次不建的表

依據系統開發規劃與邊界約束，以下功能列為「先不要做」的範疇，本次資料庫設計**明確不建立**相關資料表，說明如下：

1. **預算表（`budgets`, `budget_categories`）**
   - *不建原因*：預算功能屬於目標規劃與差異分析層，本階段核心目標在於正確收錄入帳、花費、投資與發票的實際事實流水帳。未來可在既有 `expense_categories` 基礎上外掛週期預算表，無須更動現有結構。
2. **固定收支表（`recurring_transactions`, `schedules`）**
   - *不建原因*：排程扣款、定期定額投資、每月固定房租與水電等定期範本機制，需要背景排程器（Scheduler / Cron Job）自動產生交易。目前先以手動或 API 直接記帳為主，避免引進狀態機與排程維護複雜度。
3. **載具自動匯入表（`carrier_invoices`, `carrier_accounts`, `einvoice_tokens`）**
   - *不建原因*：串接財政部電子發票整合服務平台（E-Invoice API）需要留存載具驗證碼（手機條碼驗證碼）、Token 換發與非同步佇列。本階段發票冊採手動輸入或由後端 API 批次建立，暫不保存三方載具登入憑證表。
4. **即時股價與歷史行情表（`stock_quotes`, `market_prices`, `price_histories`）**
   - *不建原因*：目前投資冊只專注於記錄個人的「交易事件流水（Transactions）」並計算「持有股數」與「加權買入成本」。未實現損益與現前市值計算依賴外部證券報價 API，目前暫不建立價格緩存表或收盤價時序表。
5. **銀行同步與開放銀行整合表（`bank_connections`, `bank_sync_logs`）**
   - *不建原因*：第三方銀行自動同步（Open Banking API 或網路銀行爬蟲）需要敏感帳密安全保管模組、雙重驗證狀態暫存與連線同步記錄。本次以手動記帳本質為核心，排除銀行同步架構。
6. **複式記帳分錄表（`journal_entries`, `ledger_lines`, `chart_of_accounts`）**
   - *不建原因*：使用者明確指定為個人實用記帳本，不採用傳統會計之借貸平衡複式記帳法（Double-Entry Bookkeeping）。帳戶餘額由收支、移轉與交割事件直接代數累加，免除龐大的會計科目表與分錄過帳表。
7. **刪除與異動稽核日誌表（`audit_logs`, `deleted_records_archive`）**
   - *不建原因*：依據「先不要做：刪除帳務列」之規範，系統預設所有帳務記錄一旦成立即永久留存（若需更正採紅字沖銷或補正交易）。因此目前不需要建立軟刪除資源回收桶或資料列歷史異動映像表。
8. **使用者帳號與多租戶共享表（`users`, `tenants`, `family_sharing`）**
   - *不建原因*：依據約束條件，本專案為單一使用者本機/個人專用記帳本，不發明使用者帳號、權限角色或家庭共享結構，全庫所有實體直接服務該單一帳本。
